# 아이폰에서 게임이 저절로 다시 시작되는 문제 (2026-10-22 ~ 23)

사용자 누나 폰: "그냥 들어가서 게임 시작해서 하고 있으면 재부팅되고, 또 뭐 좀 하려고 누르면 다시 재부팅됨." (아이폰 크롬에서는 "이 페이지를 열 수 없음" 화면도 나옴.)
사용자 질문: "IOS가 문제인걸까?"

---

## 사용자에게 (요약)

### 한 줄 답

**iOS가 고장 난 게 아니라, 게임이 메모리(특히 그래픽 메모리)를 너무 많이 써서 iPhone이 페이지를 강제로 닫은 것**으로 보는 게 가장 맞습니다. 사파리·크롬·카톡 안 브라우저 모두 아이폰에서는 같은 엔진(WebKit)이고 같은 한도에 걸립니다. PC·안드로이드는 한도가 넉넉해서 안 보였을 뿐입니다.
이번에 **전투 중 메모리를 약 887MB → 390MB(−56%)** 로 줄였습니다. 보이는 모습·소리·규칙·숫자는 그대로입니다.
**다만 진짜 아이폰에서 확인한 것은 아닙니다**(아래 "실제 아이폰으로만 확인할 수 있는 것").

### 원인을 쉬운 말로

iOS는 한 페이지가 쓰는 메모리가 정해진 한도를 넘으면 경고 없이 그 페이지를 닫고, 브라우저가 처음부터 다시 불러옵니다. 그래서 게임이 "재부팅"처럼 보입니다. 다시 불러온 직후에는 또 같은 무거운 시작을 하니 한 번 더 닫히고, 그래서 "누르면 또 재부팅"입니다.
게임이 쓰던 메모리 대부분은 세 군데였고, 최근 빌드(스킬·소리)가 원인은 아닙니다(그 둘은 합쳐서 +5%, 원래부터 무거웠음):

1. **피해 숫자 글꼴판 28장 (약 274MB).** 숫자에 쓰는 글자는 20여 개인데 영문 대문자 전부를 포함한 47글자짜리 글꼴을 8가지 색·굵기 조합마다 큰 판(1024×1024) 3~4장씩 만들고 있었습니다. 전투를 만들 때 한꺼번에 만들어 그래픽 카드에도 한꺼번에 올립니다(전투 시작 20초 안에 +150MB 폭).
2. **버튼·패널·아이콘을 그림 한 장으로 구울 때 쓴 "부드러운 가장자리용 임시 버퍼"를 안 돌려줌 (전투 236MB, 화면을 거칠수록 늘어 최대 465MB).** 구운 그림 크기의 4배짜리 버퍼인데 구운 뒤에는 아무도 안 쓰고, 화면이 바뀌어도 풀(pool)에 쌓이기만 합니다. 설정 화면 한 번만 눌러도 +250MB가 한 번에 생겼습니다("뭘 누르면 다시 재부팅"과 맞는 부분).
3. **그림 170장을 켤 때 전부 펼쳐 둠 (67MB)**, 그리고 화면을 바꿀 때 아무것도 안 돌려줘서 두 번째 전투가 첫 전투보다 더 무거웠음.

### 무엇을 바꿨나 (눈에 보이는 변화 없음)

1. 숫자 글꼴: 실제로 그리는 글자 23개만, 크기는 화면에서 쓰는 만큼(해상도 2→1)으로, 글자 사이 여백도 줄여 면당 판 1장(512×512). **28장 1024×1024 → 8장 512×512.**
2. 구운 그림의 임시 버퍼: **굽자마자 반납**(다시 구울 때만 다시 만듦), 너무 큰 구움(세로로 긴 목록 한 장)은 아예 쓰지 않음, 풀의 그림 크기를 2의 거듭제곱(300→512) 대신 16칸 단위(300→304)로, **장면을 나갈 때와 화면(팝업)이 닫힌 뒤 안 쓰는 그림 판을 정리.** 구운 결과는 화소 단위로 같음을 확인(설정 화면 비교에서 차이 0, 구운 그림 404장을 다시 구워도 차이 0).
3. 첫 터치 때 시작하는 소리 346개 굽기: 하나 끝나면 60ms 쉬고(전엔 24ms), **전투를 만드는 동안 10초·홈을 만드는 동안 2.5초는 쉼.** 전투에 필요한 소리는 전과 같이 먼저 굽습니다. 첫 터치 직후 바로 전투를 시작해도(실제 플레이어가 하는 일) 겹치지 않습니다.
4. **그래픽 컨텍스트가 사라질 때**(아이폰이 그래픽 메모리를 회수하면 일어남): 옛 빌드는 구워 둔 그림(패널·버튼·탭 바 바탕)이 빈 자리·검은 네모가 되어 화면이 깨진 채 계속 갑니다(Chromium에서 `WEBGL_lose_context`로 재현해 확인). 이제는 게임을 멈추고, 돌아오거나 4초가 지나면 **저장된 곳(마지막 웨이브 시작)에서 다시 시작**합니다. 2분에 2번까지만이라 무한 반복은 없습니다.
5. 화면 크기 변화(주소창이 미끄러질 때 등)를 프레임당 한 번으로 합치고, 같은 크기면 아무것도 안 하고, 그릴 판을 두 번 새로 만들던 것을 한 번으로.
6. **진단 페이지**: `https://kymmmm01.github.io/Project1/?scene=diag` (배포되면). 누나가 열어서 화면을 캡처해 보내면 **기종 OS 버전, 사파리인지 카톡 같은 앱 안 브라우저인지, 그래픽 카드, "페이지가 사용자 앞에서 닫힌 적"의 횟수·장소·시각**이 나옵니다. 게임이 장면·웨이브·화면이 앞뒤로 가는 순간을 기기에 적어 두고, 다음 시작 때 읽어서 판단합니다(마지막 흔적이 `hidden`이면 다른 앱으로 간 것, 그 외면 앞에서 닫힌 것).
7. **가벼운 모드(자동)**: 24시간 안에 페이지가 앞에서 두 번 닫힌 기기는 다음 시작부터 렌더 해상도 2→1.5, 소리 전체 굽기 안 함, 전투 시작 때 "나중에 쓸지도 모르는" 그림을 그래픽 카드에 미리 안 올림. 조금 흐릿하고 가끔 더 끊길 수 있지만 규칙·숫자는 그대로. 끊기지 않는 기기는 평생 못 봅니다. `?lean=1`로 강제로 켜서 볼 수 있고 `?lean=0`은 끔. 진단 페이지에 켜졌는지와 이유가 나옵니다.
8. 측정 도구를 저장소에 넣음: `tools/mem/`(README 있음). 앞으로 무거워졌는지 같은 방법으로 비교할 수 있습니다.

가장 위험한 순간들:

- **첫 터치와 "출동"이 몇 초 안에 이어질 때**(소리 굽기와 전투 시작이 겹침): 그래픽 텍스처+임시 버퍼 최대 **513 → 113MB**, Chromium 두 프로세스 합 1781 → 1221MB.

- 자바스크립트 힙 최대(원시)는 거의 그대로(170 → 168MB): 힙은 이번에 건드리지 않았습니다(아래 "손대지 않은 것").

가벼운 모드를 켜면(`?lean=1`) 같은 시나리오에서 그래픽 텍스처 111 → 73MB, 화면 그리는 버퍼 45 → 25MB, 소리 16.5 → 12.4MB (전체 합 대략 250~310MB).

### 실제 아이폰으로만 확인할 수 있는 것

- **아이폰이 이 페이지에 허락하는 메모리 한도** (기종·iOS 버전·사파리/앱 안 브라우저마다 다름). 위 숫자는 Chromium(SwiftShader) 기준 계산이고, WebKit이 캔버스·WebGL 텍스처·멀티샘플 버퍼를 어떻게 세는지는 모릅니다. 그래서 "−56%"는 **계산상**입니다. 누나 폰에서 실제로 안 끊기는지가 유일한 확인입니다.
- WebKit이 오프라인 오디오(소리 굽기) 346개를 연달아 만들 때의 행동(Chromium에서는 문제없음, 사파리엔 `requestIdleCallback`이 없어 24ms 타이머로 돌던 것을 60ms 간격으로 늦춤).
- 그림의 선명도는 Chromium에서 화소 비교로 확인했고(구운 그림은 같음, 피해 숫자 글자는 가장자리 화소가 조금 다르고 잉크 면적이 −1.7%), 아이폰 화면에서 눈으로 보는 것도 해 봐야 합니다.
- 그래픽 컨텍스트 손실 후 다시 시작하는 흐름은 Chromium에서 `WEBGL_lose_context`로 재현해 확인했지만, 실제 아이폰이 컨텍스트를 잃는 상황은 재현하지 못했습니다.
- 헤드리스 Edge는 효과 등급을 `낮음`으로 낮췄습니다. 폰은 `보통`/`높음`이라 입자·숫자 개수가 조금 더 많습니다(메모리는 몇 MB 차이).

3. 카톡 링크라면 사파리로 여는 안내/버튼(`docs/진행상황.md`에 보류로 적힌 제안)은 이번에 만들지 않았습니다. 메모리가 줄어든 효과를 먼저 본 뒤 결정하면 됩니다.

## 자세한 내용

### 1. 측정 방법

- 도구: `tools/mem/` (이 작업에서 저장소로 옮김). 메모리 조사 담당이 만든 측정 도구를 그대로 쓰고 고쳤습니다: 모든 WebGL 호출을 감시해 텍스처·렌더버퍼 바이트를 장부로 적고(`init.js`), CDP로 힙에서 캔버스·ImageBitmap·오디오버퍼·Pixi 텍스처 소스를 셉니다.
- 환경: 헤드리스 Edge(`--mute-audio`, SwiftShader), 390×844 css px·devicePixelRatio 3·터치, 게임이 잡는 그리기 버퍼 780×1688. 제품 빌드(`vite build --base /Project1/`)를 `vite preview`로 띄움. 전·후 모두 같은 장면 순서: 홈 → 첫 터치(소리 굽기) → 첫 전투(스킬 고양이 25마리·3배속·3분) → 홈 → 두 번째 전투.
- "전" 빌드는 `HEAD`(1b68b71)를 새로 빌드한 것이고 조사 담당이 잰 값과 같습니다(예: 전투 30초 그래픽 텍스처 275.4 vs 276.4MB, 임시 버퍼 236MB 같음). 조사 담당의 옛 빌드와 새로 빌드한 HEAD가 같은 그림을 그리는지는 화소 비교로 확인했습니다(차이 거의 0).
- **눈으로만 비교하지 않기**: 숫자 글꼴을 바꾼 뒤 "획이 두꺼워 보인다"고 느꼈으나 화소 계산으로는 같았습니다(잉크 화소 4122 vs 4123). 이후 모든 비교는 화소 차이로 했습니다.
- 한계: Chromium 기준. 프로세스 크기(`proc R/G/B`)와 속도는 아이폰과 무관합니다.

| 멀티샘플 버퍼 (likely cause) | 위와 같음 |
| 숫자 글꼴 (likely cause) | 위와 같음 |
| 그림 디코드 (contributor) | 안 고침 |
| 첫 터치 소리 굽기 (contributor) | 위와 같음 (`requestIdleCallback`이 없는 사파리의 24ms 타이머도 60ms로) |
| 재시작하면 새 플레이어는 튜토리얼 처음부터 | **안 고침.** 튜토리얼을 건너뛰기·재개하는 흐름은 규칙에 속해 건드리지 않음. 메모리가 줄어 이 구간 자체가 가벼워짐(튜토리얼 전투 합 계산상 약 510 → 약 260MB). 진단 페이지로 튜토리얼 중에 닫히는지 알 수 있음 |
| WebGL 컨텍스트 손실 처리 없음 | **고침.** 4번 |

| 한계 정리 | 위 "실제 아이폰으로만" |

### 3. 손대지 않은 것과 이유

- **디코드된 그림 67MB(`ImageBitmap`) 그대로.** 5곳이 화면에 올린 뒤에도 `source.resource`를 다시 읽어 구움: 소환사 베기 잔상(`view/director/sp/cut.ts`), 보스 물고기 얼굴(`view/fishArt.ts`, 적 그림), 사진 틀(`screens/shell/thumb.ts`), 배경 가장자리 색(`view/field/background.ts`), 유령(`view/field/ghosts.ts`). 닫아 버리면 그 그림이 대체 그림으로 바뀌어 모습이 달라지고, Pixi가 안 쓴 그림을 60초 뒤 내릴 때 다시 올리지 못합니다. 모든 그림을 한 번에 다루는 위험 대비 이득(약 40MB)이 작다고 봐서 하지 않았습니다. 가벼운 모드가 켜진 기기에서도 그대로입니다.
  - 후속 후보: 챕터 배경 5장(17.7MB, 한 판에 1장만 씀)과 타이틀 키아트(6MB)를 필요할 때만 읽기(`src/core/assets.ts`, 홈 챕터 카드가 쓰는지 확인 필요).
- **자바스크립트 힙.** 전투 30~60초에 104~107MB, 3분이 지나면 52~70MB로 내려옵니다. 힙 표본 조사로는 늘어난 힙의 대부분이 Graphics의 모양 데이터(선·삼각형 목록)였고, 영구 누수는 아니었습니다(고양이 상세를 6번 열고 닫으면 힙 +33MB가 90초 뒤 +4MB로 돌아옴). Pixi가 쓰지 않은 데이터를 60초 뒤(30초 간격 검사)에 풀어 주는 시간과 맞아떨어집니다. Pixi의 회수 시간을 줄이는 길(`gcMaxUnusedTime`)이 있지만, 쓰지 않은 그림을 더 빨리 내리면 탭을 오갈 때 다시 올리는 순간 끊김이 늘 수 있어 이번엔 바꾸지 않았습니다.
  - "화면에서 파괴됐는데도 연결이 남은 표시 객체 약 1,480개"는 그대로입니다(원인은 조사하지 않았습니다. 첫 전투 후 1,481개, 이후 더 늘지 않는 것은 확인했습니다. Pixi가 풀에 되돌린 그리기 묶음이 마지막 프레임의 목록을 들고 있을 가능성이 있다는 추정입니다).
- 효과 등급을 iOS에서 `보통`으로 고정하자는 제안: 입자·숫자 개수 차이는 몇 MB라 하지 않음.
- 구운 아이콘을 한 장 아틀라스로 합치자는 제안: 멀티샘플 버퍼가 없어지면서 아이콘 하나의 비용이 1배(이전 5배)로 줄어 효과가 작음.
- 소리 은행 예산(17MB): 굽는 시점만 바꾸고 예산은 그대로.
